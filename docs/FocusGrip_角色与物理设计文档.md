## 1. 人体比例

全部数值以**身高 `BH` 归一化**，改一个 `BH` 整个人等比缩放，不存在写死的像素值。取成年男性 7.5 头身。

| 部位 | 归一化 | `BH=328` 时（px） | 常量名 |
|---|---|---|---|
| 头高 | 0.133 | 43.6 | `R.head` |
| 头宽 | 0.100 | 32.8 | `R.headW` |
| 颈 | 0.038 | 12.5 | `R.neck` |
| 肩宽 | 0.245 | 80.4 | `R.shoulderW` → `SW` |
| 髋宽 | 0.150 | 49.2 | `R.hipW` → `HW` |
| 躯干（肩关节→髋关节） | 0.288 | 94.5 | `R.torso` → `TORSO` |
| 上臂 | 0.186 | 61.0 | `R.upperArm` → `UPARM` |
| 前臂 | 0.146 | 47.9 | `R.foreArm` |
| 手掌 | 0.108 | 35.4 | `R.hand` |
| 大腿 | 0.245 | 80.4 | `R.thigh` → `THIGH` |
| 小腿 | 0.246 | 80.7 | `R.shin` → `SHIN` |
| 脚长 | 0.152 | 49.9 | `R.foot` |

**由比例推导的可达半径**（`deriveBody()`）：

```
FOARM   = 前臂 + 手掌×0.40        // 让手掌真正搭到岩点上，见 §3
ARM_MAX = (UPARM + FOARM) × 0.985   = 0.370 BH ≈ 121 px
LEG_MAX = (THIGH + SHIN)  × 0.985   = 0.484 BH ≈ 159 px
LEG_MIN = (THIGH + SHIN)  × 0.34    = 0.167 BH ≈  55 px   // 腿压缩到底的下限
```

`× 0.985` 是为了不让关节绝对锁死，留一点自然弯曲。

**几处刻意的取舍**：

- 前臂比上臂短约 22%，大腿与小腿基本等长——这是真实解剖数据。旧版把四肢两节写成等长，视觉上手臂会显得过长。
- 头宽 / 头高 = 0.75，不是正圆。
- 身高 `BH = clamp(屏高 × 0.40, 200, 340)`。**这是全局唯一的尺寸开关**，岩点间距、脚点密度、可达半径都从它推导。

## 2. 物理模型

### 2.1 结构

两个 Verlet 质点承载全部重量：

```
S = 肩中点      P = 髋中点
S──P 之间是刚性躯干（长度 TORSO）
四肢不是刚体，而是「锚点 → 岩点」的长度约束
```

四肢锚点由躯干朝向实时算出（`anchors()`）：肩关节在 `S ± 肩宽/2`（沿躯干法线），髋关节在 `P ± 髋宽/2`。躯干倾斜时锚点跟着转，所以身体侧挂在墙上时肩髋位置依然正确。

### 2.2 每帧步骤

```
integrate(S), integrate(P)        // Verlet + 重力，速度衰减 0.93
STIFF = 0.90 → solveOnce() × 12   // 主求解
STIFF = 1.00 → solveOnce() × 4    // 收尾：硬约束，杜绝肢体被拉过解剖极限
```

`solveOnce()` 内的约束顺序：

1. **躯干**：把 `|S−P|` 拉回 `TORSO`，S 和 P 各承担一半位移。
2. **手**：若「肩关节 → 抓着的岩点」距离 > `ARM_MAX`，按 `STIFF` 比例把 **S** 朝岩点拽。
3. **脚**：同理作用于 **P**；另有下限——距离 < `LEG_MIN` 时把 P 推开，模拟腿不能无限压缩。

重力按身高换算，不是拍脑袋的常数：

```
GRAV = 9.8 × (BH / 1.75)    // 把 BH 当作 1.75 m
```

所以摆荡和坠落的节奏在任何屏幕尺寸下都是同一个物理量级。

### 2.3 为什么这样就"对"

身体是被岩点吊着的，不是摆好姿势画上去的。双手挂点 → 手臂拉直、身体自然垂下；脚踩上点 → 腿把髋顶起来，重心前移。玩家不需要理解这些，但每一帧的姿势都是解出来的，不是插值出来的。

## 3. 手脚必须真的接触岩点

这是这版最核心的修正。三道保证：

**① IK 段长包含手掌。**
绘制用二节 IK（`ik(root, end, l1, l2, bend)`）会把末端钳制在 `l1+l2` 内。如果 `l2` 只算前臂，手臂全伸时画出来的手会**停在离岩点一段距离的地方**。所以令 `FOARM = 前臂 + 手掌×0.40`，并让 `ARM_MAX` 与之一致——手一定落在点上。脚同理：IK 末端就是**踝关节**，鞋从踝往外画，鞋底压在岩点上。

**② 收尾硬约束。**
Verlet 在两次求解之间会有超调。最后 4 次迭代把 `STIFF` 提到 1.0，实测四肢最大伸展率 **1.000**——任何一帧都不会出现橡皮筋般被拉长的肢体。

**③ 脚点管理器 `manageFeet()`，每帧运行。**

```
对每只脚：
  已踩点 → 距离 > LEG_MAX×0.995 或 < LEG_MIN×0.55 → 蹬脱（realistic，不强行黏住）
  没踩点 → 在候选里挑一个：
      硬条件：LEG_MIN×0.9 ≤ 距离 ≤ LEG_MAX×0.93，且必须在髋部下方
      打分  ：越接近「髋 ± 0.22BH 横向、0.42BH 下方」越好
      惩罚  ：跨到身体对侧 +0.40BH；和另一只脚抢同一个点 +0.60BH
```

候选来源 = **已爬过的线上岩点** + **脚点小岩块**。

### 脚点小岩块（`USE_FOOT_CHIPS`）

线上岩点纵向间距 0.42 BH，只靠它们踩脚会经常够不着。所以按关卡种子确定性地补一批小岩块：起步区 4 个（正对起攀站立位），之后每两个线上岩点的中点各 1 个、横向随机偏移 ±0.26 BH。

它们**不参与任何判定**，画得更小更暗（`rgba(140,115,88,.55)`，半径 0.62×主岩点），视觉上一眼能区分"线上的点"和"随便踩的点"。不想要就把 `USE_FOOT_CHIPS` 改成 `false`——判定逻辑完全不受影响，只是脚会更常悬空。

**袖口与裤腿**：上衣覆盖上臂前 30%，短裤覆盖大腿前 34%，同色扁平叠加。

### 鞋：外八 + 鞋底压在岩点上

两条规则：

**① 鞋尖朝身体外侧（外八）**

```js
shoeAngle(髋锚点, 接触点, side)
  = clamp(0.24 + atan2(向外的水平分量, 向下的竖直分量) × 0.30, 0.02, 0.85)
```

腿越向外张，鞋尖压得越低；下限 0.02 rad 保证鞋尖**永远不会翘起来**。左脚通过 `shoeLocal()` 做镜像（先镜像后旋转），所以两只鞋是对称的，不是同一只鞋转了 180°。

**② 鞋底压在岩点上表面，不是鞋悬在岩点中心**

物理解出来的接触点是鞋底的位置，踝关节要在它**斜上方**：

```js
踝 = 接触点 + shoeLocal(-脚长×0.10, -鞋高×0.95, a, side)
IK 目标改为踝，而不是接触点
```

实测三帧采样：鞋底与接触点的竖直偏差 1~5 px（岩点半径约 19 px），踝关节高于接触点 18 px，两只脚鞋尖朝外均通过。

## 4. 路线布局与可达性

原 `makeLevel` 产出的是归一化坐标 `nx∈[0.16,0.84]`，落到屏幕上相邻两点水平差可达 265 px，**远超 121 px 的真实臂展**——旧版角色是摆拍的所以无所谓，现在会直接卡死。

`layoutLevel()` 里加了一道钳制，随机性和左右交替的路线性格都保留：

```
STEP   = 0.42 × BH                        // 纵向步距 ≈ 一次真实的移动
spread = min(屏宽×0.52, 1.35×BH)          // 横向铺开范围
相邻两点水平差钳制在 ±0.30 × BH 内
```

`0.42` 与 `0.30` 的取法：斜边 `√(0.42² + 0.30²) = 0.52 BH`，而伸手极限约 `0.37 BH` + 身体上移量，留够余量但不至于让路线变成一条直线。

## 5. 换手时序

一次成功抓点的完整时间线（`g.anim` 从 0 走到 1，约 0.42 s）：

```
fill 填满
  → 主动手立刻挂上下一个岩点（B[leadKey].hold = 新点）
  → anim 开始，此时双手同时挂点
  → anim > 0.55：旧支撑手松开
  → 身体被新点单点吊住，物理自然把人拽上去并摆荡
  → anim ≥ 1：i++，supKey 与 leadKey 互换（左右手交替）
  → pickFeet() 重选踩点
```

主动手是哪只由几何决定：下一个点在左边就用左手。之后每爬一格自动交替，和真实攀岩一致。

蓄力阶段主动手的伸出量：`reach = clamp(F / win.hi) × 0.88`，从胸前静止位插值到目标点，并按 `ARM_MAX` 钳制——所以"力气不够手就够不着"这件事是**看得见**的。

## 6. 甩飞（`triggerWreck`）

判定阈值沿用原设计：`F ≥ win.hi + RED_MARGIN(0.19)`。

表现改为按正确比例摆一个四肢张开的姿势，整体绕重心旋转 + 抛物线飞出（`vy += 900·dt`，角速度 7~12 rad/s）。1.15 s 后回到 `lastGoodI`，`resetBodyTo()` 重新解算落位并重选踩点。

## 9. 已知限制

1. **没有真正的碰撞体**。身体不会被岩点挡住，极端姿势下肢体可能从岩点上方掠过。Jam 尺度下不值得为此上完整碰撞。
2. **`manageFeet` 是贪心的**，只看当前帧最优，不做全局规划。偶尔会出现"其实换另一只脚更顺"的踩法。
3. **甩飞是刚体旋转**，不是真布娃娃。PRD 把 ragdoll 列为 Should，如果时间够，可以把 §2 的求解器复用成多质点链，改动量不大。
4. **`layoutLevel()` 在窗口 resize 时会重排路线**，当前进度 `G.i` 保留，但角色会瞬移到新位置。演示时别中途改窗口大小。

## 10. 与硬件联调时要注意的

角色层完全不关心力度从哪来。`Input.value` 是 0~1 的归一化值，只有 `stepMechanics` 读它。硬件同学那边把 `{force: 0-200}` 推过来，改这两行即可：

```js
const INPUT_MODE = 'network';
const WS_URL     = 'ws://<ESP32 的 IP>:8080';
```

PRD 第 4.3 节要求的滤波与个人化标定还没做，建议加在 `Input` 的 `onmessage` 里（滑动平均 + 开局取最大值归一化），这样游戏逻辑依然一行不用改。
