# FocusGrip「指哪爬哪」· 技术栈

FocusGrip 的核心 AI 挑战在于：**如何在浏览器端，实时融合视觉、触觉、行为与自报四类异构信号，在信号稀疏、噪声大且极度保护隐私的约束下，准确判断用户的注意力状态并生成个性化干预。** 这本质上是一个边缘端多模态时序融合问题。以下按技术层次展开。

---

## 一、多模态边缘 AI 融合引擎（核心）

这是整个系统 AI 含金量最高的部分，解决三个关键问题。

**问题一：异构信号如何统一表征？**

系统同时接入四类信号源，频率、维度和物理含义完全不同：

| 信号源 | 维度 | 采样率 | 数据类型 |
|--------|------|--------|----------|
| 面部关键点（Face Landmarker） | 468 点 × 3 维 | ~30fps | 连续时序 |
| 手部关键点（Hand Landmarker） | 21 点 × 2 手 × 3 维 | ~30fps | 连续时序 |
| 姿态关键点（Pose Landmarker） | 33 点 × 3 维 | ~30fps | 连续时序 |
| 压力传感器（FSR + ESP32-S3） | 1 维 | 50Hz | 连续标量 |
| 桌面行为（鼠标空闲 + 活跃窗口标题） | 离散事件 | 轮询 | 布尔/类别 |
| 用户主动标记 | 离散事件 | 按需触发 | 布尔 |

系统对每个通道分别提取高层语义特征：面部通道不传原始 468 点，而是计算眨眼速率、张嘴速度、头部晃动角速度三个统计量；手部通道计算手腕位移幅值、关节移动方差、手指屈伸速率；姿态通道计算躯干晃动幅度。三个视觉通道各自输出一个归一化的"节律分数"（0–100），压力通道输出均值、方差、超阈值事件计数与波形趋势。最终送入融合层的是一组跨模态对齐后的语义特征向量，而非原始像素或坐标。

**问题二：什么是"异常"？——个性化基线建模**

ADHD 用户的"躁动"表现因人而异。同一个人上午和下午的基线也不同。系统采用**会话级在线基线自适应**策略：每次摄像头开启后，前约 90 帧（约 3 秒）用于静默建立该通道的均值 μ 与标准差 σ，后续帧以 `|x - μ| / σ` 计算偏离度。基线不做跨会话持久化——页面刷新或重新开启摄像头后重新标定。这种设计既保护隐私（不存长期生物特征），又避免了固定阈值在不同用户间的误判。

**问题三：多通道信号冲突怎么办？——交叉验证与融合判定**

单通道超基线很常见（比如只是打了个喷嚏），真正的 ADHD 相关状态波动通常体现在多个维度。系统采用**双通道交叉验证规则**：仅当两个及以上通道同时高于自身基线时才触发"多通道变化"提示。这本质是一种轻量级的无监督异常检测——不依赖标注数据，不输出概率，而是在信号空间里寻找跨模态的共现异常模式。融合判定逻辑同时考虑信号的优先级：用户主动标记为最高优先级（用户知道自己状态不对），其次为多通道变化，再次为单通道持续偏离，最后为日常周期性提示。

所有推理均在浏览器主线程的 requestAnimationFrame 循环中完成，MediaPipe 模型通过 WebAssembly 在 CPU 上本地执行，GPU 不参与。整个融合管线从视频帧到语义特征到融合判定的端到端延迟控制在 100ms 以内。

## 二、LLM 驱动的个性化干预生成

融合引擎判定需要干预后，系统将当前状态的结构化快照（压力均值/趋势/波动次数、各通道节律分数与基线偏离度、多通道变化分数、用户标记状态）通过本地 Next Route Handler 代理发送至小米 MiMo Chat Completions API（mimo-v2.5-pro）。这里的架构设计有两个关键决策：

**① 服务端代理，密钥不落前端。** MiMo API Key 仅存放于 `.env.local`，浏览器通过 `POST /api/suggestion` 间接调用，前端代码零敏感信息暴露。

**② 只传抽象数值，不传原始数据。** 请求体中不包含任何视频帧、图像、关键点坐标或可还原为个人身份的信息。MiMo 只看到"当前压力均值 67，面部节律偏离基线 1.8σ，手部稳定"这样的统计描述，生成的建议自然也是非诊断式的温和引导（"给手指一个小出口""试试轻敲桌面"）。所有建议文案均以低压力、可拒绝的方式呈现，避免对用户构成二次焦虑。MiMo 不可用时自动降级为前端硬编码的兜底建议库。

## 三、智能触发与多终端分发

AI 的干预不仅依赖"状态检测"，还依赖"时机判断"。桌面行为监测模块持续跟踪两个信号：鼠标空闲时长与前台活跃窗口标题。当检测到 YouTube、哔哩哔哩、微信等应用连续前台超过 10 分钟，或鼠标超过 10 分钟未移动时，系统判定用户可能已滑入无意识分心状态——此时不是去批评用户，而是在行为模式刚呈现趋势时就"截胡"：弹出攀岩关卡选择弹窗，引导用户将注意力转移到指力微练习中。

干预信息通过两条路径分发：一是像素心流网页中的上浮建议气泡，二是桌面 MindReset Quote/0 电子墨水屏（296×152）。墨水屏选择本身是一个重要的交互设计决策：它的低刷新率和纸质质感天然具备"不打扰"的气质。本地 Node.js 桥接进程每分钟轮询建议接口，以 `title + body` 生成内容指纹去重，仅在建议内容变化时通过 Dot. Text API（UTF-8 JSON + Bearer Token 认证）推送，避免电子墨水屏无意义的重复刷新。同时支持 Image API 发送 296×152 PNG，适配扩散抖动算法优化黑白显示。

## 四、指力攀岩游戏引擎

作为干预体系中的"行动转化层"，游戏本身也在承担 AI 系统的部分职能——它把 ADHD 注意力训练目标内化为玩法机制。

**物理引擎**：自研 Verlet 积分 + IK 长度约束求解器，按 7.5 头身真实人体比例建模。肩/髋两个质点承载全部重量，躯干为刚性约束，四肢为"锚点→岩点"的长度约束。重力按身高比例换算（`G = 9.8 × BH/1.75m`），确保不同屏幕尺寸下物理量级一致。每帧 16 次约束求解迭代（12 次标准 + 4 次硬约束收尾），实测四肢最大伸展率精确控制在 1.000，杜绝橡皮筋拉伸。

**判定系统**：力度窗口抓点（绿区匹配 + 0.3–0.5s 稳定判定）+ 持续保持点 sloper（力度漂出窗口进度回退）。力度反馈 = 冲动控制训练，sloper = 持续注意力训练，短关卡（60–120s）= ADHD 注意力跨度适配。游戏本身即干预，不需要额外"治疗模块"。

渲染层使用 HTML5 Canvas 单文件架构，搭配 Matter.js 驱动 ragdoll 甩飞效果，音频通过 Howler.js 管理。六条难度递增路线共用一套关卡生成器，按种子确定性生成岩点布局、力度窗口与脚点小岩块。

## 五、硬件与数据链路

**指力训练板**：硅胶/3D 打印外壳 + 单颗 FSR 薄膜压力传感器 + ESP32-S3 微控制器。FSR 原始信号经 ADC 后由 ESP32 以 50Hz 频率通过 Wi-Fi（WebSocket）或 USB（Web Serial）推送至浏览器，数据格式为 `{force: 0-4095}`。软件端进行滑动平均低通滤波 + 开局个人化标定（用户用力捏一次取最大值），归一化至 0–100% 后送入游戏判定与压力波形绘制。

压力数据同时复用于像素心流检测——同一路传感器信号既驱动攀岩游戏，也作为多模态融合的触觉通道输入。

---

## 六、隐私与伦理架构

系统的 AI 能力建立在严格的隐私约束之上，这不是附加条款而是架构前提：

- MediaPipe 三个模型（Face/Hand/Pose Landmarker）的推理全程在浏览器本地执行，通过 WebAssembly 在 CPU 运行，视频帧不离开浏览器进程；
- 发送至 MiMo 的仅为抽象统计值，不包含原始图像、关键点坐标或可还原身份的信息；
- 摄像头关闭后，视频轨道、模型实例与会话基线立即清除，不做任何持久化；
- 个性化基线仅存在于当前会话内存中，跨会话不存储，兼顾个性化与匿名性；
- 所有建议均为非诊断式引导，系统不用于诊断 ADHD、预测医学事件或给用户贴标签。
